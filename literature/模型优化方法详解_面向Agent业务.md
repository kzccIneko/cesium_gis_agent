## 第零章 · 先建立一个基本概念：优化的是什么

先把三个容易混的词分清，后面所有内容都建立在这个区分上。

| 词 | 英文 | 指的是什么 |
|---|---|---|
| **训练** | Training | 让模型从数据里**学**东西。需要 GPU 大量计算，几十分钟到几天 |
| **推理** | Inference | 用训好的模型**回答**问题（就是我们系统平时在做的事） |
| **模型优化** | Model Optimization | 一个统称。目标是让模型**更小 / 更快 / 更准 / 更听话**，具体手段有十几种 |

**关键认知**：这十几种方法服务于四个不同的目标，选哪个取决于**你的瓶颈在哪**。

| 你的瓶颈 | 该考虑的方法 |
|---|---|
| 显存装不下 / 磁盘太大 | 量化、剪枝、蒸馏 |
| 回答太慢 | 量化、KV Cache 优化、投机解码、剪枝 |
| 输出格式不合法 | 约束解码 |
| **模型"不懂"你的业务 / 判断不准** | **微调（后训练）、上下文工程** |
| 压根不是模型的问题（流程乱、没记忆） | **改 Agent 架构** |

**本项目的瓶颈是最后两条**，这一点决定了后面的所有取舍。记住这句话，下面就好理解了。

## 第一章 · 不改模型的方法（推理侧优化）

这类方法的共同点：**模型权重不动**，只是换个存法或换个用法。做起来快、风险低。

### 1.1 量化（Quantization）—— 把权重"压缩存储"

**是什么**：神经网络里的"权重"就是一大堆小数（比如 `0.0237`、`-1.5582`）。
原始精度是 16 位浮点数（FP16），每个数字占 2 字节。量化的意思是：
**把这些小数映射到一个很小的整数表里**，比如只保留 256 个档位（8 位），或 16 个档位（4 位）。

打个比方：原图是一张 1600 万色的照片，量化相当于把它存成 16 色调色板——
文件小了 4 倍，肉眼看差别不大，但放大看细节会有损失。

**为什么有效**：跑模型时的瓶颈往往**不是算力，而是显存带宽**——
每生成一个字，都要把全部权重从显存里读一遍。权重小了 4 倍，读得就快 4 倍。

**本项目的实例**：

| 对象 | 量化前 | 量化后 | 效果 |
|---|---|---|---|
| Agent 大脑（Qwen3.5-4B） | 约 8 GB（FP16） | **2.6 GB**（Q4_K_M） | 装进 6 GB 显卡（常驻 4.5 GB） |
| ONNX 地貌分类模型 | 3.79 MB | **0.96 MB** | 缩小 3.9 倍，精度几乎不变 |

**为什么选 `Q4_K_M` 这个档位**（不是 Q2 也不是 Q8）：

- **Q4** = 4 位。再往下（Q2/Q3）压缩率更高但精度掉得明显，实测对推理质量影响较大
- **K** = K-quant，一种分块量化策略：模型里不同层对精度敏感度不同，
  K-quant 会给敏感层留更多档位、给不敏感层更少，比"一刀切"更聪明
- **M** = Medium，这一档有三个变体 S（小）/ M（中）/ L（大），M 是速度与质量的平衡点

一句话：**Q4_K_M 是"能在 6 GB 卡上跑起来"与"回答质量还能用"之间的折中**。

**优劣**：

| ✅ 优点 | ❌ 缺点 |
|---|---|
| 立竿见影，不需要训练、不需要数据 | 精度必然有损失（Q4 通常 1–3%） |
| 显存、磁盘、速度同时受益 | 量化到 4 位以下质量下降明显 |
| 有现成工具（llama.cpp 自带） | 量化后的模型不能再直接微调（要回原始权重） |

### 1.2 约束解码（Constrained Decoding）—— 强制输出格式

**是什么**：大模型是一个字一个字往外蹦的，它"想"输出什么格式完全靠自觉。
约束解码是在生成时加一个**过滤器**：每步只在"符合语法"的候选字里挑，
不符合的直接屏蔽。等于给模型戴上一副"只能走这条路"的缰绳。

**本项目的实例（而且是个否定结果）**：
我们原本计划用 llam.cpp 的 **GBNF 文法**（一种描述"合法输出长什么样"的规则文件）
来保证工具调用的 JSON 一定合法。实测 24 条样本：

| 指标 | 不约束 | 加约束 | 变化 |
|---|---|---|---|
| JSON 解析成功率 | 100% | 100% | **0** |
| 意图判定准确率 | 91.7% | 91.7% | **0** |
| 单条耗时 | 3.1 s | 4.1 s | **+32%** |

**结论：不采用。** 原因有二：
1. 它想解决的问题（JSON 不合法）在我们这里**根本不存在** —— 本来就是 100%
2. 两组的失败样本**完全相同**（「统计珠峰坡度比例」被判成拒答），
   这是**语义理解**问题，而约束解码只管**语法**，管不了语义

> 这条否定结果的价值在于：它把问题精确定位到了"模型能力"，而不是"输出格式"。

**优劣**：适合"格式要求严格、模型能力足够"的场景；对"模型根本理解错了"无能为力。

---

### 1.3 剪枝（Pruning）—— 把没用的连接删掉

**是什么**：模型里有很多权重接近 0（几乎不参与计算），剪枝就是**把这些删掉**。
好比一支球队里有几个几乎不上场的替补，裁掉能省工资。

分两类，这个区分很关键：

| 类型 | 做法 | 能否真正提速 |
|---|---|---|
| **非结构化剪枝** | 零散地删掉单个权重，矩阵还是那么大（只是很多位置是 0） | ❌ GPU 按固定形状算，删了零也要占位置 |
| **结构化剪枝** | 整行、整列、整个注意力头地删 | ✅ 矩阵真的变小了，能提速 |

**为什么本项目不做**：
1. LLM 本身已经训练得很稠密，能白删的不多，收益不如量化直接
2. 结构化剪枝通常要**重新训练**才能恢复精度，成本高于收益
3. 我们要的是"装进 6 GB 显卡"，量化已经解决了

> 剪枝在视觉模型（如那个 ONNX 分类模型）上有时有意义，对 LLM 性价比不高。

### 1.4 蒸馏（Knowledge Distillation）—— 大模型教小模型

**是什么**：先有一个大而强的"**老师模型**"，再训练一个小而快的"**学生模型**"，
让学生去模仿老师的输出。关键细节是：学生学的**不只是标准答案，还有老师的"倾向"**。

举例说明这个区别：分类任务是"这是山脊还是山谷"。
- 只学标准答案 → 学生只学到"答案是山脊"
- 学老师的输出分布 → 学生学到"老师认为 80% 是山脊、15% 是缓坡、5% 是山谷"，
  这层"犹豫的程度"包含了额外信息，学生能学得更好

**本项目已经有一个蒸馏实例**（你之前做的那个）：

```
老师：Geomorphons 算法   ← 确定性规则，算得准但慢
   ↓ 用它给大量地形打标签
学生：CNN 小模型（ONNX）  ← 学老师的标签，推理快 133 倍
```

这就是**典型的蒸馏**：用一个慢而准的老师，去造数据训练一个快的学生。

**为什么 Agent 大脑不做蒸馏**：
1. 需要一个更强的老师 —— 而我们**没有云端大模型可用**（这是产品定位）
2. 蒸馏要大量数据 + 训练算力，成本远高于直接微调
3. 我们的问题不是"模型太大跑不动"，而是"判断不够准" —— 微调更对症

**优劣**：

| ✅ 优点 | ❌ 缺点 |
|---|---|
| 能得到一个真正小而快的模型 | 必须有更强的老师（通常要花钱调大模型 API） |
| 学生可任意缩小 | 训练成本高、周期长 |
| 能传递"软信息"（老师的倾向） | 学生上限受老师限制 |

### 1.5 KV Cache 优化 —— 别重复算已经算过的

**术语解释**：**KV Cache（键值缓存）** 是 Transformer 的一个机制。
生成每个字时，模型都要"回看"前面所有的字。如果每次都重算一遍，复杂度是平方级的。
KV Cache 就是把前面算过的中间结果**存起来复用**。

**本项目的实例**：批量跑评测时，"系统提示词 + 工具定义"这 4900 个 token
对每一道题都是相同的，却每次都要重新算一遍。我们做了**前缀复用**：

| | 单样本耗时 |
|---|---|
| 不复用 | 6.94 s |
| 复用前缀 | **4.26 s（快 1.63 倍）** |

**踩过的坑（写进代码注释了）**：一开始用了库自带的 `save_state / load_state`，
结果**完全没有加速**（0.99 倍）。原因很反直觉 —— 它内部会把一个
`(8192 × 151936)` 的浮点数组完整拷贝两次，**那个数组有 4.98 GB**，
光是拷贝的开销就把省下的时间吃光了。最后改用底层接口 + 手动设置 token 计数才成功。

> 这个坑的启示：**"用了某个优化技术" 不等于 "真的变快了"，必须实测**。

---

### 1.6 投机解码（Speculative Decoding）—— 小模型起草、大模型审核

**是什么**：让一个**小模型**先飞快地写几个字（草稿），再让**大模型**一次性
检查这几个字对不对，对的就整段采纳。因为大模型检查一批字比逐个生成快，
总速度能提升 2–3 倍，且**输出与纯大模型完全一致**（不用怕质量下降）。

**本项目不做**：需要同时装两个模型，6 GB 显存装一个 4B 都很紧张。

---

### 1.7 上下文工程（Context Engineering）—— 不改模型，改"喂什么给它"

**是什么**：不改任何权重，只改**提示词、工具描述、历史记录的组织方式**。
说它不算"模型优化"也行，但**在本项目里它的收益排第一**。

**本项目的实例**：意图分层架构。

最初想让模型在做规划时**顺便判断意图**（analysis / knowledge / action / chat / refuse 五选一）。
把意图规则写进主提示词 → 模型完全无视，全部判成 analysis；
把意图章节挪到提示词**最末尾**（最靠近用户问题、注意力最强处）→ **仍然无效**。

原因：提示词里那套工具选择规则（决策表 + 三条硬规则 + 负向清单，是 98.75% 准确率的来源）
**太强势**，模型一旦进入"我是规划器"的角色，就不管问什么都去规划 `compute_slope`。

**唯一有效的解法是拆成两次调用**：
1. 先用一段**极短、且完全不含工具规则**的提示词，单独判断意图（约 900 字符）
2. 只有判定为"分析"时，才交给原来那套完整规划器

| ✅ 优点 | ❌ 缺点 |
|---|---|
| 零训练成本、改完立刻见效 | 多一次调用（分析题 +约 1 秒） |
| 不损失精度、可随时回退 | 提示词之间有相互干扰，需要实测调优 |
| **能解决"换种说法就失效"以外的多数问题** | 解决不了"模型确实不懂这个领域" |

## 第二章 · 改模型的方法（训练侧优化）

这类方法**会修改模型权重**，所以需要训练：准备数据 → 跑 GPU → 得到新模型。

### 2.1 全参数微调（Full Fine-tuning）

**是什么**：拿一个预训练好的模型，用你的数据**把全部参数都更新一遍**。

**显存怎么算**（以 4B 模型为例，这个账要会算）：

| 组成 | 占用 | 说明 |
|---|---|---|
| 模型权重 | 8 GB | 40 亿参数 × 2 字节（FP16） |
| 梯度 | 8 GB | 每个参数配一份"该往哪改" |
| 优化器状态 | 16 GB | 常用的 AdamW 优化器，每个参数额外记 2 份 |
| 激活值 | 若干 | 前向计算的中间结果，要留着算反向 |
| **合计** | **32 GB+** | 实际通常 40 GB 以上 |

**本项目：不可行。** 但它是理解后面两个方法的基础 —— 记住"权重 : 梯度 : 优化器 ≈ 1 : 1 : 2"这个比例。

---

### 2.2 PEFT / LoRA —— 只训练一小块"旁路"

**先解释 PEFT**：Parameter-Efficient Fine-Tuning，**参数高效微调**。
一个统称，指"只训练极少量参数"的所有方法。LoRA 是其中最有名的一种。

**LoRA 是什么**（Low-Rank Adaptation，低秩适配）：

原模型的权重是一个大矩阵 `W`。全参微调是把 `W` 直接改掉；
LoRA 的做法是**不动 W**，而是在旁边学一个"增量" `ΔW`，用的时候加回去：

```
最终权重 = W + ΔW     其中 ΔW = B × A
```

`A` 和 `B` 是两个**瘦长的小矩阵**，它们的乘积尺寸和 `W` 一样，但参数量只有 `W` 的百分之几。
打个比方：不改原书的正文，只在旁边贴一张薄的勘误表，读的时候两本对照着看。

**几个必须知道的名词**：

| 名词 | 是什么 | 我们用的值 | 为什么 |
|---|---|---|---|
| **rank（秩）`r`** | 旁路矩阵有多"宽"。越宽学得越多，也越容易过拟合 | **16** | 常见范围 8–64。我们数据只有 800 条，用大 r 会过拟合；r=16 是"够学"与"不过拟合"的平衡点 |
| **alpha** | 缩放系数，控制增量叠加时的强度 | **32**（= 2r） | 社区惯例是 `alpha = 2×r`，相当于给学习率一个温和的放大 |
| **lora_dropout** | 训练时随机"丢掉"一部分旁路连接，防止死记硬背 | **0.05** | 小数据集的常规防过拟合手段 |
| **target_modules** | 给哪些层加旁路 | `"all-linear"` | 见下面「为什么这个参数最要紧」 |
| **adapter** | **训练产出的那个增量文件**（就是 ΔW 本身） | 61 MB | 它**不含原模型**，所以小 —— 是个"补丁" |

**特别解释你问到的 `adapter`**：
它就是 LoRA 训练结束后的产物，文件里只有 `A` 和 `B` 两个小矩阵。
用的时候必须**配上原模型**才能工作。所以：
- 它只有几十 MB（对比原模型 8 GB）
- **训练用哪张显卡与它无关** —— 云端 4090 训出的 adapter，拿回本机配原模型直接用
- 这也正好符合你"模型文件总量 ≤5 GB"的约束

**为什么 `target_modules="all-linear"` 这个参数最要紧**：
Qwen3.5 是一个**混合架构**模型（同时用了两种注意力机制）。
它的 Gated DeltaNet 层里，投影层叫 `in_proj_qkv` / `in_proj_z` / `in_proj_a` / `in_proj_b` / `out_proj` ——
这些名字**不在任何 LoRA 教程的默认列表里**。如果按老教程写 `q_proj,v_proj`，这些层会被完全漏掉，
**训练出来的 adapter 等于没学到东西**。

PEFT 库提供的 `"all-linear"` 是"给所有线性层都加旁路"的架构无关写法。
我们实测：**命中 187 个线性层、可训练参数占比 1.42%**，确认覆盖到了那 5 个 GDN 投影层。
**这一步是先验证后实施** —— 如果不验证就开训，可能白花几小时才发现没训到点子上。

### 2.3 QLoRA —— 量化底座 + LoRA

**是什么**：Quantized LoRA。把底座模型**先量化到 4 位**（省 3/4 显存），再在上面加 LoRA 训练。

**显存对比**（4B 模型）：

| 方法 | 峰值显存 | 6 GB 卡 |
|---|---|---|
| 全参数微调 | 40 GB+ | ❌ |
| LoRA（FP16 底座） | ~10 GB | ❌ |
| **QLoRA（4 位底座）** | **6.04 GB（实测）** | ⚠ 贴线打满 |

**我们实测的数字**（这是本项目最有价值的一组测量之一）：

| 模型 | 加载后显存 | 训练峰值 | 6 GB 卡余量 |
|---|---|---|---|
| Qwen3.5-0.8B | 0.72 GB | 2.04 GB | +3.96 GB |
| **Qwen3.5-4B** | **2.90 GB** | **6.04 GB** | **−0.04 GB（越界）** |

结论有两条：
1. **技术上能跑**：4B 的 4-bit 加载 13.3 秒、前向反向都成功、13 种线性层全部命中
2. **但不该在本机跑**：这还是单次计算、序列长度 512 的理想情况，真实训练要连续几百步，
   加上显存碎片毫无缓冲；而这台笔记本的散热问题已经实测过（功耗墙从 75W 掉到 47W，
   推理阶段就反复崩）

→ **可复用的独立结论：4B 模型做 QLoRA 微调，最低硬件门槛约 8 GB 显存。**

**QLoRA 的两个技术细节**（为什么不是"量化完直接训"）：
- 需要 `prepare_model_for_kbit_training()`：把 LayerNorm 这类不该量化的层转回 FP32，
  并开启梯度检查点，否则训练不稳定
- 量化后的模型**不能用 `.to(device)` 移动**，必须一开始就用 `device_map` 指定设备

### 2.4 对齐训练：SFT / DPO / ORPO / GRPO

这几个词都是"怎么教模型"的不同方式。按"教什么"分两类：

**第一类：教它"该输出什么"（监督式）**

| 方法 | 全称 | 教什么 | 需要的数据 |
|---|---|---|---|
| **SFT** | Supervised Fine-Tuning，监督微调 | "看到 A，就回答 B" | **输入 + 标准答案** |

**第二类：教它"哪个回答更好"（偏好式）**

| 方法 | 全称 | 核心思路 | 需要的数据 |
|---|---|---|---|
| **DPO** | Direct Preference Optimization，直接偏好优化 | 给"好回答 vs 坏回答"的成对样本，让模型提高好回答的概率 | 成对偏好标注 |
| **ORPO** | Odds Ratio Preference Optimization | 把 SFT 和偏好合成一步做完，省一次训练 | 同上 |
| **GRPO** | Group Relative Policy Optimization，群组相对策略优化 | 让模型对同一个问题生成一组答案，按得分高低自己调整（DeepSeek-R1 用的就是它） | **可自动打分的任务** |

**本项目为什么选 SFT**：

关键判据是 **"我能不能自动造出标准答案"**。

- 我们的任务是**意图分类**（这句话属于 analysis / knowledge / action / chat / refuse 哪类）
- 这类任务的标签是**确定的**：模板写完，答案是哪个类别就定死了
- 所以我们可以**自动生成 800 条"输入 → 正确答案"**，零人工标注

而 DPO / GRPO 需要的是"哪个更好"或"能自动打分的奖励"：
- 意图分类没有"好坏"，只有"对错" —— 这天然就是 SFT 的形状
- 如果做的是"工具链规划"，倒是可以设计自动打分（比如工具序列和标准答案比），
  那才轮到 GRPO 出场

> 一句话：**能定义"标准答案"就用 SFT；只能定义"更好"才用 DPO/GRPO。**

---

### 2.5 继续预训练（Continued Pre-training, CPT）

**是什么**：用大量领域文本**再喂一遍**，让模型"补知识"。注意它和 SFT 的区别：

| | 继续预训练 | SFT |
|---|---|---|
| 教什么 | **知识**（这个领域有哪些概念、事实） | **行为**（看到这类问题该怎么回应） |
| 数据形式 | 大段文本，无需标注 | "输入 → 答案"配对 |
| 成本 | 高（要几十 GB 语料） | 低 |
| 适用 | 模型完全不懂这个领域 | 模型懂，但做得不对 |

**本项目不做**：4B 模型对"什么是坡度、什么是 DEM"是懂的；
我们的问题是"它判断用户意图不稳" —— 这是**行为**问题，SFT 对症。

---

## 第三章 · Agent 特有的优化（既不改模型，也不只是提示词）

这是**本项目收益最大的部分**，也是最容易被忽略的部分。

### 3.1 编排结构 —— 贡献 +56.2 个百分点

**是什么**：规定 Agent"先做什么、再做什么"的流程结构。
对比一下两种做法：

- **无结构（ReAct 式想到哪做到哪）**：模型拿到问题就边想边调工具，
  调完看结果再想下一步，容易迷路
- **有结构（状态图编排）**：固定的 `规划 → 执行 → 反思 → 总结` 四阶段

**实测**（固定模型与提示词，只改工作方式）：

| 工作方式 | 总准确率 | 多工具类 |
|---|---|---|
| 无状态图的临时多轮试探 | 40.0% | **5.0%** |
| 完整状态图编排 | 96.2% | **95.0%** |
| **差值** | **+56.2 点** | **+90 点** |

多工具类从 5% 到 95% —— 等于**从"完全不会做多步任务"到"会做"**。
这是所有优化手段里投入产出比最高的一项，而且**不需要任何训练**。

### 3.2 自我校验 / 反思 —— 贡献 +3.7 点

**是什么**：让 Agent 在每个工具执行后**自己检查一下结果是否合理**，不合理就重试。
实测：开启 96.2% vs 关闭 92.5%。

**踩的坑**：反思节点一度把一次正常结果**连判三次"不合格"**，导致流程卡死。
修复方式是加"僵局检测"：如果工具明明成功了、模型却连续要求重试同一件事，就强制通过。

### 3.3 记忆与上下文管理

**是什么**：让 Agent 记住之前聊过什么、分析过哪里。详见 Week 7 的实现（三层记忆 + 指代消解）。

**关键设计原则**（也是你之前提的）：
**规则只负责"补事实"，模型负责"做决策"**。
「这个地方」指哪里，是**已经发生过的事实**，查数据库即可；
用户究竟想干什么，才需要模型的语义理解。两者不能混。

### 3.4 工具描述与 Schema 设计

**是什么**：工具的"说明书"怎么写，直接影响模型调不调它、怎么调。
同一个功能，描述写得含糊，模型就会漏调或传错参数。
本项目 11 个工具都用 JSON Schema 描述并做了多轮措辞打磨。

### 3.5 RAG 知识注入 —— 我们实测是负收益

**是什么**：RAG（Retrieval-Augmented Generation，检索增强生成）——
先从知识库里检索相关段落，塞进提示词给模型参考。

**本项目的实测结论**：把知识库接到规划环节，工具选择精确率**反而从 96.2% 降到 91.2%（−5.0 点）**。
失败样本集中在"检索片段里的专业术语诱使模型多插了一个工具"。

→ 已改为**默认关闭**，只在术语与原理类问答时启用。
**这个负结果如实写进了报告和简历** —— 因为它是真的，且比"报喜不报忧"更经得起追问。

### 3.6 级联 / 路由（Cascade / Routing）

**是什么**：先用便宜快的小模型试，拿不准再升级到贵的大模型。
本项目全本地、只有一个模型，暂不适用；但如果将来引入更好的模型，这是省算力的常用手段。

### 3.7 多智能体分工（Multi-Agent）

**是什么**：把任务拆给多个角色（规划者 / 执行者 / 检查者），各自用独立的提示词。
**本项目暂不做**：4B 模型在多个角色间切换容易失焦，且延迟会翻倍。
当前用"单模型 + 阶段化提示词"达到类似效果。

## 第四章 · 对比总表（骨架）

| 方法 | 一句话是什么 | 需要什么 | 收益点 | 本项目 |
|---|---|---|---|---|
| **量化** | 把权重从高精度压到低精度 | 无需训练 | 显存↓磁盘↓速度↑ | ✅ 用了（Q4_K_M） |
| **约束解码** | 生成时强制输出格式合法 | 一份语法规则 | 格式合规 | ❌ 实测零收益 +32% 延迟 |
| **剪枝** | 删掉不重要的权重 | 结构化剪枝需重训 | 模型变小 | ❌ 对 LLM 性价比低 |
| **蒸馏** | 大模型教小模型 | 更强老师 + 训练算力 | 小模型能力强 | ✅ 已有（Geomorphons→CNN） |
| **KV Cache 优化** | 复用算过的中间结果 | 改推理代码 | 速度 1.63× | ✅ 用了 |
| **投机解码** | 小模型起草、大模型审核 | 同时装两个模型 | 速度 2–3× | ❌ 显存不够 |
| **上下文工程** | 改喂进去的内容，不改权重 | 只需实验 | 可解多数问题 | ✅ 意图分层架构 |
| **全参微调** | 所有参数都更新 | 40 GB+ 显存 | 上限最高 | ❌ 不可行 |
| **LoRA** | 只训一小块旁路 | ~10 GB 显存 | 成本低、产物小 | ✅ 用其变体 |
| **QLoRA** | 量化底座 + LoRA | **6–8 GB 显存** | 门槛最低的微调 | ✅ 实测 4B 峰值 6.04 GB |
| **SFT** | 教"看到 A 回答 B" | 输入-答案对 | 行为纠正 | ✅ 57.5%→97.5% |
| **DPO / GRPO** | 教"哪个更好" | 偏好对 / 可打分 | 对齐人类偏好 | ❌ 无偏好标注 |
| **继续预训练** | 喂领域语料补知识 | 大量语料 | 补知识缺口 | ❌ 缺的是行为不是知识 |
| **编排结构** | 规定 Agent 的流程 | 改代码 | **+56.2 点** | ✅ 收益第一 |
| **自我校验** | 做完自己检查 | 改代码 | +3.7 点 | ✅ |
| **记忆管理** | 记住聊过什么 | 改代码 | 多轮可用 | ✅ |
| **RAG 注入** | 检索资料塞提示词 | 知识库 | 术语问答 | ⚠ 实测 −5.0 点，默认关 |

## 第五章 · 为什么本项目最终落在"QLoRA + SFT"

把上面的地图收拢到一条决策链：

**第一步：先问"瓶颈是不是模型"。**
评测显示主集准确率 98.75%，但**隔离测试发现模型自己判定意图只有 91.7%** ——
差额来自外层正则规则在替模型兜底。

**第二步：能不能不训模型就解决？**
试过 GBNF 约束解码 → 零收益（问题在语义不在格式）。
试过把意图规则写进提示词、还试过挪到最末尾 → 模型完全无视（工具规则太强势）。
结论：**这个问题绕不过模型本身**。

**第三步：那就必须训。选哪种训法？**
- 全参微调 → 40 GB，不可行
- LoRA（FP16）→ 10 GB，6 GB 卡不可行
- **QLoRA → 实测 6.04 GB，贴线**（本机勉强、云端宽裕）
- DPO/GRPO → 没有偏好标注，任务形状也不对
- 继续预训练 → 缺的是"行为"不是"知识"

→ **QLoRA + SFT，任务选"意图路由"。**

**第四步：数据从哪来？**
没有人工标注预算 → 用模板 + 地名槽位 + 口语化前后缀 + 难例加权**自动构造 800 条**，
标签由模板决定（确定性），零人工成本。

**第五步：结果。**
在 80 条**留出集**（训练时未见过）上，意图判定 **57.5% → 97.5%（+40.0 点）**，
loss 0.56 → 0.0043，产物 adapter 仅 **61 MB**。

**第六步：在哪训？**
本机 6 GB 贴线 + 笔记本散热已知会崩 → **云端单次训练**（约 15 分钟、0.6 元），
产物拉回本机使用。这一步之所以可行，正是因为 **adapter 与训练硬件无关**。
