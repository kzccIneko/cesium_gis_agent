指标释义（每条都带本项目的真实例子）

评测对象是「用户说一句中文 → Agent 给出一条可执行的工具调用链路」。 下面每一项都说明：怎么算、拿本项目哪条样本举例、这个数字低了意味着什么。

一、三项样本类别怎么划分

类别定义 例子考的是什么
单工具调用
40 条
一句话用一个工具就能完成。「计算成都周边的坡度」→ [compute_slope]；「统计珠峰多少比例的坡度在 15 度以下」→ [zonal_statistics]。考的是能不能从一句话里认出该用哪个工具，以及不要画蛇添足。
多工具串联
40 条
需要两个以上工具按依赖顺序串起来，后一步要吃前一步的产出。「下载四姑娘山的真实高程数据并计算坡度」→ download_srtm → compute_slope；「找一条从 A 到 B 坡度小于 15 度的路线」→ compute_slope → compute_cost_surface → plan_route。这一项最能说明它是「Agent」而不是「函数调用」：没有编排能力的模型一次只能吐一个工具，此项理论上限为 0。
越界拒答
20 条
超出系统能力范围，正确行为是明确拒绝而不是硬编一个答案。「分析火星地形」「预测明天天气」→ 应回答「超出能力范围」。考的是会不会胡编。地理分析场景下，编一个看似合理的错误结论比直接说不会更危险。

二、每个指标怎么算

工具链精确率tool_exact
怎么算模型给出的工具调用序列，与标准答案逐项相同、顺序相同、不多不少，才算 1 分。
本项目例子「下载四姑娘山的真实高程数据并计算坡度」标准答案 [download_srtm, compute_slope]，模型输出同样两项 → 1 分；「锡林郭勒草原哪里好走」标准答案 [compute_cost_surface]，模型输出 [compute_slope, compute_cost_surface] → 0 分（多做了一步）。
说明什么衡量的是：用户一句话下达后，Agent 规划的这条流水线能不能不多不少地直接跑通。它同时考「选对工具」和「不做无用功」，是最严的一项。
工具集合 F1tool_set_f1
怎么算只看用到了哪些工具的重合度，不看顺序、不计重复。
本项目例子期望 {compute_cost_surface}，预测 {compute_slope, compute_cost_surface}：预测 2 个里命中 1 个 → 精确率 1/2；期望 1 个全被命中 → 召回率 1/1；F1 = 2×0.5×1.0÷(0.5+1.0) = 0.667。
说明什么总精确率 80.0% 而集合 F1 91.5%，这个 11.5 个百分点的差额说明：模型基本都选对了该用的工具，丢分主要来自「多调一步或漏调一步」，不是「选错工具」。
顺序正确率tool_order
怎么算标准答案的步骤序列里，有多大比例被模型按原来的先后顺序保留下来（最长公共子序列长度 ÷ 期望长度）。
本项目例子期望 [A, B, C]，预测 [A, C, B]：能保住的最长顺序是 [A, B] 或 [A, C]，长度 2 → 2÷3 = 0.667。
说明什么衡量的是步骤依赖有没有搞反。比如必须先有坡度栅格才能算通行代价，顺序反了整条链就跑不通。当前 95.0% 说明这类错误很少。
bbox 参数正确param_bbox
怎么算分析范围的四个边界值 [西, 南, 东, 北] 与标准答案相差都在 0.01° 以内（约 1.1 km），且四个位置的顺序不能错。
本项目例子标准答案 [103.5, 30.2, 104.5, 31.0]（成都周边），模型输出 [103.5, 31.0, 104.5, 30.2] —— 四个数值都有，但南北写反了 → 判 0 分。经纬度顺序错了等于分析区域错了。
说明什么⚠ 当前 100% 是虚高，暂时不能写进简历：评测集里的 bbox 与地名词典共用同一份数据，模型相当于在抄答案。用词典外区域另做的 12 条对照集，真值 12/12。
拒答正确率refusal_correct
怎么算两个方向都算：越界问题必须明确说做不了；正常问题不许推脱。任一方向违反即 0 分。
本项目例子「分析火星地形」「预测明天天气」这类越界问题（20 条），回答「超出能力范围」→ 1 分；「计算成都周边的坡度」这类正常问题（80 条），如果也答「做不了」→ 0 分。
说明什么当前 20/20 且工具类零误拒。这一项要两头看：只把拒答做对很容易（全都拒绝就满分），难的是同时不误拒正常请求。
每样本 LLM 调用次数n_llm_calls
怎么算完成一条任务平均要问大模型几次。
本项目例子理想情况：一次规划直接给出完整链路 → 1 次。如果参数填错被反思节点打回重来，就会变成 2 次、3 次。
说明什么接入 LangGraph 前是 2.17 次，现在是 1.05 次，意味着一次规划就能把链路定完，几乎不需要回头重试。
单样本延迟 p50elapsed_p50
怎么算100 条样本的耗时从短到长排序，取正中间那条的耗时。p90 是排在第 90 位的那条。
本项目例子100 条里最快的约 4 s、最慢的因 GPU 重试超过 40 s。用平均值会被这几条慢样本拉偏，看不出常态。
说明什么当前 p50 = 9.8 s，在本机 RTX 2060 6GB + Qwen3.5-4B Q4_K_M 全量本地推理下测得，没有任何云端 API 参与。

Week 6 · 把 Agent 装进三维地理系统

起因：W5-6 交的是一个独立网页。用户实测后指出三条硬伤 —— 脱离主系统用不上地图上下文、「你好」被当成越界任务拒答、 且回复只有纯文字，没有数据 / 表格 / 图表 / 图层。
诊断结论：不是前端没画图表，是后端数据通路断了 5 处 —— 产物目录没挂载、字段名单复数对不上、只返回本地路径没有 URL、 执行记录丢弃结构化结果、寒暄走错分支且模板泄漏。
W6-1 ✅让产物能被访问
工具把 GeoJSON/CZML 写进 geoagent_artifacts/，但 HTTP 只挂载了 cesiumjs_debug_outputs/ —— 前端根本下载不到。
验收加 /artifacts 挂载；产物返回值补 url 字段。GET /artifacts/xxx/slope.geojson 可下载
W6-2 ✅把结构化结果传出来
工具算好的「每级坡度多大面积、8 类地貌各占几成、路径多长爬升多少」在回传时被丢掉了 —— 执行记录只留了工具名和耗时。
验收新增 result_view.py 裁剪白名单；JSON 里能看到 zonal 的 classes 数组
W6-3 ✅寒暄不再被当成越界任务
以前「你好」也要跑一遍大模型规划，19 秒后回一句机器话，还把内部提示词模板（「向用户说明…」）当成答案吐出来。
验收规则直答：19.2 s → 0.2 s，回复是人话；拒答不再是模板泄漏
W6-4 ✅导出地图加载能力
加载后端的整套管道（分批、注册侧栏、数值提示）是封闭的，Agent 拿不到，只能另写一套 —— 那就是两套渲染行为。
验收新增 window.TerrainBackendBridge（只加导出，未改内部逻辑）
W6-5 ✅面板进主系统
Agent 不再是独立页面，而是主页面里第 15 个悬浮窗，与「坡度坡向分析」同款拖拽/折叠/置顶。
验收顶部菜单「智能体分析助手」可开面板；主 HTML 仅末尾追加 2 个 script
W6-6 ✅结果变成表和图
按结果类型分派：分级统计表 + 面积柱状图、地类构成饼图 + 图例色卡、路径里程/爬升指标卡。
验收问「统计坡度分级」能出表格 + 图表 + 指标卡，不再是纯文字
W6-7 ✅结果落到三维地球上
矢量产物一键叠加，自动注册进主系统的侧栏图层树，可显隐、可定位。
验收真机冒烟：侧栏图层数 0 → 1，出现 slope_deg 图层
W6-8 ✅所见即所问
分析范围默认取当前相机视野，相机移动时实时刷新；视野过大（如对着整个地球）会被拦下并提示放大。

W6-9 ✅入口独立且常驻（用户反馈）
上一版把入口塞在「空间分析」下拉里 —— 但 Agent 不是空间分析工具，它该是贯穿全系统的对话入口（对标商业 GIS 的做法：独立菜单 + 悬浮按钮）。
验收顶部**独立常驻菜单项**，按项目约定只用图标（顶部栏本身常驻，不需要再加悬浮按钮）
W6-10 ✅用 Cesium 自带地形，不再拿合成地形糊弄（用户反馈）
用户没上传 DEM 时，后端会回退到合成的正弦曲面，算出来的坡度与实际地表毫无关系（冒烟截图里整片绿油油就是它）。
验收前端在视野内按 128×128 采样 Cesium World Terrain，落成 GeoTIFF 交给后端；贡嘎山实测平均坡度 4.79° → 20.33°，最大坡度 8.56° → 54.25°
W6-11 ✅意图分层：别让模型只会分析地形（用户反馈，本轮核心）
planner 只给了模型两条路：做地形分析 / 拒答。于是「这里是什么地方」「你有什么功能模块」「跳转到海南省」全被拒答或硬做分析。用户判断得准：不是模型参数小，是我们没给它别的路走。
验收五类意图（analysis / knowledge / action / chat / refuse）+ 两段式分类（先用极短提示词单独定意图，是 analysis 才进工具链）+ 地名反查 + 省级地名库（93 条）

Week 7 · 对话记忆与上下文管理

起因：用户实测反馈两条 —— ① Agent 不保留、也不阅读上下文， 上一轮刚聊完五指山，下一句「跳转到这个地方」它答"请提供具体地名"； ② 同样的操作换个地名就变样，「跳转到五指山」秒回， 「跳转到阿尔卑斯山」却先跑几分钟地形采样才跳转。
诊断结论：两条都不是模型不够聪明，是架构缺口 —— 第二条尤其反直觉，后端意图判断一直是对的（9 个句式实测 8 个正确）， 问题出在前端抢跑：请求还没发出去，它就先无条件采样了 16384 个高程点。
W7-1 ✅记忆存储层
SQLite 五张表：turns（会话轮次）/ spatial_focus（空间焦点卡片）/ region_memory（常用区域，含访问次数与时间衰减）/ user_profile / confirmed_facts。刻意不用 LangGraph checkpointer —— 它存的是整个图状态快照（我们的 state 里有 DEM 路径、产物列表、trace 等大对象），而且项目是双运行时，checkpointer 只在图分支生效会造成行为分叉。

一个被实测否定的技术方案：GBNF 约束解码

我原本的计划是给意图分类加上 GBNF 文法约束（基础设施早就写好了但一直没调用）， 理由是"JSON 偶尔不合法"。实测把这个假设证伪了 —— 无约束时 JSON 解析成功率本来就是 100%，GBNF 对决策准确率零影响，还慢 32%。 两组失败的样本完全相同，说明错因是语义理解，而 GBNF 只管语法。 这条否定结果把问题精确定位到了"模型能力"而非"格式"，直接决定了下一步方向。
指标实测值说明
JSON 解析成功率100.0%（24/24）格式问题在实测中不存在
意图判定准确率91.7%（22/24）失败的 2 条：「统计珠峰坡度在15度以下的比例」→ refuse、「这片区域属于什么地貌类型」→ knowledge

设计取舍（面试会问的三点）

  • 为什么不用 LangGraph checkpointer？它解决的是"断点续跑"（存整个图状态快照）， 而记忆解决的是"理解上下文"。我们的 state 里有 DEM 路径、产物列表、trace 等大对象， 每轮快照既慢又脏；且项目是 LangGraph + 自研循环双运行时， checkpointer 只在图分支生效会造成行为分叉。
  • 为什么短期只截断不摘要？已实测 4B 模型做"转述"会改坏事实； 且 Lost-in-the-Middle 实测注意力呈 U 型、中段信息召回率约 20% —— 历史塞得越多整体准确率越低，与信息是否在窗口内无关。
  • 为什么指代消解用规则而不是让模型做？代词指向什么是已经发生过的事实 （库里记着上一轮的 bbox），查一下即可；让 4B 去猜等于抽奖。 但意图判断仍交给模型 —— 规则只补事实，不替模型做决定， 否则就会回到用户批评过的"只会回答写死的问题"。

读数据前必须知道的三件事

  • 精确率 ≠ 集合 F1：总体精确率 80.0% 但集合 F1 有 91.5%—— 说明模型工具基本选对了，丢分在「多一步／少一步」，不是选错工具。 精确率是最严口径，错一步即判整条错。
  • bbox 参数 100% 不能写进简历：100 条用到的 16 个地名全部来自 source='eval'（词典直抄自标准答案），属开卷。 无泄漏对照（12 个评测集外地名）真值 12/12，样本量还不足以支撑指标。
  • v6／v7／v8 三次独立改版都恰好停在 80.0%：此前判定为「标注噪声天花板」， 本次逐条归因后修正了这个判断——16 条失败里有 11 条是模型真实缺陷、 5 条是约定缺失，不是噪声。详见上方归因表。
